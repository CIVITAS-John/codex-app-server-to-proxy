# Codex compatibility

The proxy targets one app-server contract at a time. The current runtime dependency is `@openai/codex` **0.169.0**, pinned exactly in `package.json`. Its generated experimental TypeScript and JSON Schema contract is checked into `protocol/`, with the version and generation commands recorded in `protocol/VERSION.json`. The package-owned executable supplies normal startup and protocol generation; an explicit `--codex-path` must report the same version. A different Codex release needs a contract review before it can run behind the proxy.

| Compatibility boundary                    | Current behavior                                                                                                                                       | Consequence of a Codex update                                                                                                                                             |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| JSON-RPC and generated types              | Generation uses the pinned package with `--experimental`; `npm run check:protocol` compares a regenerated temporary tree with the checked-in contract. | Review method, notification, and field changes before changing translation or policy code. Regenerate with `npm run generate:protocol`; do not hand-edit generated files. |
| Model catalog and direct client functions | The proxy installs a temporary Responses Lite override for 0.169.0.                                                                                    | Recheck direct and parallel function-call behavior before removing the override. A passing schema check alone does not establish model behavior.                          |
| Codex home and authentication             | A proxy-owned Codex home is selected per canonical root and bound endpoint; only `auth.json` is synchronized from the ordinary Codex home.             | Review on-disk cache/config formats and token handling before reusing that home with a new pin.                                                                           |
| Continuation state                        | Each root and bound endpoint has a separate durable response store with schema version 0.                                                              | Review the persisted record format and restart behavior; migrate an incompatible format explicitly or reject it without rewriting it.                                     |

## Temporary model catalog override

Codex 0.169.0 can route models marked `use_responses_lite` through code mode, turning declared client functions into nested callbacks. The proxy clones `models_cache.json` into `models.no-responses-lite.json`, sets `use_responses_lite` to `false` for every model, and removes `tool_mode` from entries that originally used Responses Lite. It also sets `include_plugin_usage_instructions: false` on every model to suppress generic plugin guidance, and removes `"clock"` from `experimental_supported_tools` so `clock.curr_time` is not registered. The source cache remains Codex-owned and unchanged by this transformation.

A marked top-level `model_catalog_json` block in the selected home's `config.toml` points to the clone. Installing it preserves unrelated configuration but replaces any previous top-level catalog selection. The override is specific to the current pin; remove it only after a reviewed runtime and opt-in live contract show that direct, batched client functions work without it. See [user-facing behavior](../README.md#temporary-responses-lite-override) and the [app-server protocol reference](codex-app-server.md#pinned-compatibility-note).

At each new proxy process, startup makes one bounded catalog refresh attempt through a private app-server with a fresh temporary Codex home. It copies ordinary configuration without the static catalog selection and uses the selected home's credentials. Only a newly written cache with the pinned client version and nonempty valid models replaces the selected cache. Startup then rebuilds the clone and restarts the private app-server so its startup-only catalog selection takes effect. On refresh failure, the previous cache is retained with a warning; readiness still requires a usable override. Recovery of an app-server within the same proxy process does not repeat the fetch. `GET /v1/models` sees the resulting catalog frozen for that process and starts no model turn.

## Homes, credentials, and continuation state

| Data                  | Default location                                                      | Compatibility rule                                                                                                                                                                                                                                                                                            |
| --------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Codex home            | `~/.codex-openai-proxy/<root-hash>/<family>-<port>/codex-home`, or `--codex-home` | Separate per root and bound endpoint and from the ordinary `~/.codex` home. It contains the login, model cache, override, and Codex configuration. |
| Authentication source | `$CODEX_HOME/auth.json` or `~/.codex/auth.json`                       | Default `--sync-auth always` copies only a missing or strictly newer source credential. `--sync-auth never` leaves the proxy home independent. A recovered login can write back only to an existing older source after a pulled credential proved unusable. Shared rotating refresh tokens remain race-prone. |
| Continuation store    | `~/.codex-openai-proxy/<root-hash>/<family>-<port>/state`, or `--state-dir` | Stores opaque response-to-thread mappings and pending client tool calls for 30 days. The current schema is version 0; malformed or foreign-version records are not trusted. Uninstalling the npm package does not remove this state. |

[Instance directories](../README.md#instance-directories) defines the path components and overrides, and what happens to data from the former root-only layout. The continuation schema did not change; [durable response mappings](continuation.md#durable-response-mappings) covers its temporary-file handling. Errors with literal `willRetry: true` keep Codex in charge of retries, as described in [capacity errors](../README.md#capacity-errors).

Existing 0.163.0 proxy homes and schema-version-0 continuation stores can be reused on 0.169.0 without proxy migration. Codex keeps its SQLite filenames and applies an [additive native migration](https://github.com/openai/codex/blob/rust-v0.169.0/codex-rs/state/migrations/0062_threads_attached_parent.sql) for attached thread ownership. The [credential document](https://github.com/openai/codex/blob/rust-v0.169.0/codex-rs/login/src/auth/storage.rs) remains `auth.json`; Codex manages its new `auth.lock`, and the proxy still synchronizes only the credential document. The catalog refresh preserves provider/auth identity and accepts a replacement cache only for the current pin. The proxy does not rewrite stored response-to-thread mappings for this upgrade. See [authentication](../README.md#authentication) and [continuation](../README.md#continue-a-codex-thread).

## Verification boundary

The proxy explicitly disables optional automatic instruction context on thread start and resume, clears configured developer text, and disables project instruction discovery. Permission and environment context are suppressed only for the `disabled` sandbox. Built-in goal, user-input, clock, sleep, image-generation, and apps tools are removed for every sandbox; client-defined tools are unaffected. Client system/developer history and managed policy retain their existing roles. These prompt defaults change behavior without changing the HTTP schema or continuation-store format; existing transcript content is retained. See the [pinned controls and context limits](codex-app-server.md#pinned-compatibility-note).

The 0.163.0 to 0.169.0 review preserves public request and response shapes. Managed human command checkpoints stay fail-closed, new item telemetry stays private, and unmapped error classifications retain existing terminal handling. See the [pinned source review](codex-app-server.md#pinned-compatibility-note) for the protocol and Responses Lite findings.

On 2026-11-17, all seven core live scenarios passed on Windows with Codex 0.169.0 and `gpt-6-luna`, within the 32-response ceiling. The exact core count was not retained. The system-prompt suite initially interrupted its final SSE answer at the two-response limit because it treated reasoning configuration metadata as pending work. After correcting the test guard, the aggregate and SSE cases both passed in a separate two-response run. The proxy runtime and both ceilings are unchanged.

The Linux/macOS/Windows pull-request matrix and separate registry checks remain required before release.

The 2026-10-21 live run on 0.163.0 used only `gpt-6-luna`: six of seven core scenarios passed with 20 upstream responses (19 parent, one child), and both system-prompt cases passed with two responses. Web search returned successfully but exposed no `webSearch` lifecycle. Two isolated repeats passed; the final repeat used exactly one upstream response and confirmed correlated `webSearch` start/completion plus matching HTTP usage. The earlier repeat's exact response count was not reported, but its six-response guard remained active. This is partial live evidence, not a green full-suite run or a calibrated normal count. The intermittent missing lifecycle remains unexplained; runtime payloads were not saved.

Child-agent starts can arrive as `subAgentActivity` instead of `spawnAgent`. The proxy preserves only `kind` and `agentThreadId` in the existing `x_codex` activity extensions; agent paths remain private and legacy collaboration output is unchanged. The nonce-handoff contract requires exactly one child start and its raw provider completion. It verifies the child reply through `agentsStates` or, after completed activity, that child's completed thread history via `thread/read`, which starts no model work. The historical targeted live scenario passed on 2026-09-22 with `gpt-6-luna` under the existing 32-response maximum; six other scenarios were skipped.

The default `npm run check` gate is deterministic and offline. It checks generated protocol drift, types, translation, and failure paths; `npm run test:package` separately checks the packed CLI offline. Neither gate can prove model choices, authentication against a real account, or remote npm publication. The separately selected live configuration uses `gpt-6-luna`, runs serially, and caps the core contract at 32 deduplicated upstream responses plus two for the system-prompt contract. The release checklist tracks external CI, registry, and live evidence separately. Do not infer a normal model-call count from the ceiling. See [live test instructions](development.md#live-contract-tests) and [release checklist](../RELEASE.md).

When changing the Codex pin, use the repository's `update-codex` workflow, inspect the generated diff and the behavior boundaries above, run the offline and packed-package gates, and record the compatibility and persistence decision here. Live verification remains an explicit, separately budgeted action.
