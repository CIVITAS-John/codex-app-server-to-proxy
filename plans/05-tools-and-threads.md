# Stage 05: Dynamic tools and thread reuse

## Goal

Support client-defined tools across requests while preserving safe Codex thread reuse.

## Work

1. Translate Chat Completions function tools to app-server `dynamicTools` with experimental capability enabled.
    - Tools are thread-scoped in app-server. Canonicalize the definition and reject a changed tool set on continuation.
    - Register only top-level functions so `item/tool/call` correlation never depends on `namespace`.
    - Validate function names against the app-server constraints (`^[a-zA-Z0-9_-]+$`, 1 to 128 characters) with OpenAI-shaped errors.
2. When app-server issues `item/tool/call`, correlate name, call ID, arguments, thread, turn, and pending JSON-RPC response.
    - Route callbacks centrally by thread to exactly one active owner; per-request event listeners and listener-count inference are not ownership mechanisms.
3. Stream standard `delta.tool_calls`, durably persist the batch's call metadata, interrupt the turn, and end the HTTP response with `finish_reason: "tool_calls"` and the exact usage the interrupt flushes.
    - `turn/interrupt` flushes `thread/tokenUsage/updated` within milliseconds on the pinned app-server (live-verified 2026-07-26), then `turn/completed status:"interrupted"` and the idle boundary.
    - Leave every captured `item/tool/call` unanswered; the interrupt already cancelled them app-server side. A failed interrupt durably invalidates the pending batch and fails the HTTP response without exposing unusable tool calls; those app-server requests are likewise unanswered rather than resuming an ownerless turn.
    - App-server can still dispatch a late `item/tool/call` after the interrupt and lease release (observed live 2026-07-26: the interrupt cancels the call server-side but its request still arrives). Ignore an ownerless call whose thread has a durable pending batch, exactly like the captured ones; keep `-32602` correlation mismatch for threads without one, where app-server is genuinely still waiting. Compatibility consequence: no client-visible change — the batch already captured is authoritative and the model re-issues any cancelled call on continuation.
    - Nothing server-initiated outlives its originating HTTP request anymore.
4. Persist full pending-call metadata (`pendingCalls`: call ID, name, exact stringified arguments) so tool results survive proxy restarts and expire only with normal mapping retention.
    - Derive implicit-correlation call IDs from `pendingCalls`; do not persist a duplicate `callIds` field.
5. On the next request, locate the pending calls per the Stage 01 correlation decision (by `previous_response_id`, or by `tool_call_id` alone if that proves safe for unmodified clients).
    - Require the assistant tool-call message plus exactly one matching `role: "tool"` result per required call.
    - Reject missing, duplicate, foreign, or already-consumed IDs.
    - Accept a tool-ending continuation only for a pending-tool mapping. Reject the same shape against a ready mapping with HTTP 409 `tool_results_without_pending_call`; never reinterpret tool output as user text.
6. Deliver the results by resuming the idle thread, injecting each pending call as a complete `function_call`/`function_call_output` pair via `thread/inject_items`, and starting the next turn — with empty `input` when the request ends in a tool message (live-verified accepted).
    - Always inject the pair: the interrupted turn never persisted its own `function_call` item, and an unpaired output is silently ignored (live-verified).
    - Durably mark the mapping non-replayable before injection. If that write fails, do not inject; if injection fails or later bookkeeping cannot be saved, retry still returns 410 instead of risking duplicate pairs.
    - Treat the later transition from the fail-closed tombstone to `superseded` as best-effort bookkeeping; it cannot weaken the durable replay guard.
7. Support multiple parallel tool calls and out-of-order result messages while responding to app-server in observed arrival order.
    - Feed notifications and dynamic server requests through one bounded FIFO ingress stream so requests cannot overtake preceding reasoning, text, or internal-tool activity.
    - Every fresh thread opts into raw events. A new declared direct `function_call` raw item or unmatched dynamic callback opens a batch; the correlated `rawResponse/completed` closes it. Merge both sources in arrival order, deduplicate matching IDs, and exclude raw IDs already present in submitted assistant history.
    - On queue overflow or transport failure, abort the active turn and reject every queued server responder.
8. Store opaque response-to-thread mappings atomically in the state directory.
    - For every completed-response continuation, first require a valid, unexpired mapping.
    - Then inspect the mapped thread through app-server (`thread/read` returns stored status without resuming) and verify that its status and effective policy are resumable.
    - Treat `thread/resume` as the final authoritative check and handle a state change between inspection and resume as a rejected continuation.
9. Bind continuation records to the canonical tool set, model, reasoning effort, cwd, and effective policy. Reject any mismatch.
10. Add retention, pruning, corrupt-file recovery, and current-shape validation for the local mapping store.
11. Detect replayed continuation requests and make behavior idempotent where possible; otherwise return a clear conflict.
12. Serialize access per thread: a thread runs at most one active turn.
    - Immediately reject a request arriving while another request owns the same thread with an OpenAI-shaped HTTP 409 conflict; never queue or interleave it.
    - Acquire admission and dynamic-tool routing atomically as one owner-specific lease, then release that lease at cleanup. A failed or losing setup cannot release another request's ownership.
13. Never call `thread/start` when a request supplied `previous_response_id`.
    - Reject unknown, expired, archived, deleted, busy, policy-incompatible, or otherwise non-resumable references with the Stage 01 error mapping, preserving whether the client may retry. Drop malformed records during load rather than retaining a `corrupt` record state.
14. Reject a `previous_response_id` that is no longer its thread's newest completed response with the distinct Stage 01 superseded-reference error.
    - Resuming would silently append after later turns.
    - `thread/fork` with `lastTurnId` is the only faithful branching mechanism and stays out of v1 unless the Stage 01 spike proves it.

## Acceptance criteria

- Offline tests cover one tool, parallel tools, fragmented arguments, large results, mismatches, duplicates, replay, interrupt and injection failures, disconnect, cancellation, same-thread HTTP 409 conflicts, and every non-resumable continuation state.
- A completed thread resumes after proxy/app-server restart using only `previous_response_id`.
- Unknown or non-resumable `previous_response_id` values never create a new thread, including a superseded response on a multi-response thread and a thread that changes state between preflight and `thread/resume`.
- A pending tool continuation succeeds after restart from persisted call metadata alone.
- Mapping writes survive abrupt termination without corrupting other records.
- One opt-in live scenario requires two independent client tool calls in its initial parallel batch, then completes three consecutive full-history tool-result continuations with `gpt-5.6-luna` using at most four model calls before restart continuation.

## Implemented decisions

- The versioned state file is `continuations.json` under `--state-dir`. Writes use same-directory temporary files followed by atomic rename; corrupt files recover as an empty, untrusted store.
- Mapping retention defaults to 30 days. An older completed response becomes `superseded` as soon as a newer response is recorded for the same thread.
- Tool definitions are recursively key-sorted with explicit UTF-16 code-unit ordering and SHA-256 hashed. The ordering is independent of process locale and ICU data. This prerelease correction intentionally changes hashes produced by the former locale-sensitive ordering before the persistence format ships. Continuations bind that hash together with model, optional reasoning effort, root working directory, and the effective-policy hash. Reasoning effort, including its omission, matches by plain equality; the unreleased schema-version-0 reader has no compatibility-only binding flag.
- Ready and pending-tool records retain the optional exact cumulative `usageTotal` boundary the next response subtracts from: the latest complete total the response reported, or the boundary that response started from when app-server attributed nothing to it. A suspension that observed no usage therefore hands its model requests to the continuation rather than stranding them, and an all-zero boundary from a fresh thread is a meaningful value that must persist like any other. Records missing fields required by the current unreleased shape are dropped on load.
- **Decision reversal (2026-07-26): interrupt-based tool calls replace parked turns.** Live spikes against codex 0.145.0 established three facts: a parked turn's usage flushes only ~10–11 s after `item/tool/call`, while `turn/interrupt` flushes it in 1–3 ms; `thread/inject_items` (a stable API) delivers a later tool result as a complete `function_call`/`function_call_output` pair, and the model answers from it without re-calling the tool — an unpaired output is silently ignored because the interrupted turn never persisted its own `function_call` item; and `turn/start` accepts empty `input`, so a continuation ending in a tool message needs no synthetic user text. The proxy therefore interrupts every dynamic-tool turn at its batch. Compatibility consequences: `tool_calls` responses return promptly with exact usage (including reasoning tokens for never-continued calls); tool results survive proxy restarts; `--tool-timeout` and `--usage-grace` were removed; interrupting the codex-side turn means the tool result reaches the model in a fresh turn on the same thread rather than by resuming the original turn.
- Interrupt at the tool call ends the codex-side turn, so the "second round from the same turn" resume path and the process-local responder registry no longer exist. The former five-minute pending deadline is gone; pending mappings expire with normal retention.
- Two abandonment cases deliberately keep the exact-`last` fallback rather than adding a supersede protocol: a client that disconnects immediately after the tool-call frame, and a continuation that races in before the tool-call response finishes. Both can leave the record without a boundary, so the continuation maps exact `last` — never a double count.
- **Decision reversal (2026-07-28): cancelled dynamic tool calls are not answered at all.** Answering them `-32003` for JSON-RPC hygiene was pointless work — the interrupt has already cancelled them app-server side — and app-server logs each unmatched response at `ERROR` level, so every successful tool-call response ended with proxy warnings that read like a failure. The proxy now sends nothing for a request the interrupt cancelled, and `-32003` is gone. Compatibility consequence: none client-visible; Chat Completions has no standard tool-failure bit, and app-server needs no response for a request it no longer tracks.
- **Decision (2026-07-29): interrupted turn IDs remain process-local correlation tombstones.** App-server can dispatch a cancelled dynamic callback after the same thread has already started its continuation. The proxy recognizes that stale `(threadId, turnId)` even while a new owner holds the thread and leaves the callback unanswered, instead of routing it into the new turn and producing `Dynamic tool correlation mismatch`. The bounded tombstones disappear with the app-server transport generation and are recorded before the interrupt round trip, because a lost interrupt response does not prove the turn survived. This assumes app-server never reuses a turn identifier within one thread and transport generation; a reused identifier would silently discard the live calls of the turn that reused it. Compatibility consequence: stale cancelled callbacks no longer fail an otherwise valid continuation; genuine unowned correlation failures are still rejected.
- One response store lives for the proxy server lifetime. Replacing or removing app-server disposes the old continuation generation, rejects late callbacks until close, and closes the old transport so active executions wake without writing stale mappings; durable pending mappings need no per-responder cleanup. Buffered frames are ignored after logical transport close.
- The pinned protocol accepts `dynamicTools` only on `thread/start`, not `thread/resume` or `turn/start`. Consequently a pending tool-result request and every later completed-thread continuation must repeat the original canonical tool set. A 3-tool thread cannot resume in place with 2 tools; v1 rejects that request rather than silently creating a different thread.
- Implicit tool continuation is enabled by default: `tool_call_id` values must jointly identify exactly one unexpired pending mapping in the durable store, so it now survives restarts too. `--implicit-tool-continuation false` disables this compatibility mode and requires `previous_response_id`; unknown or ambiguous IDs never fall back to a new thread.
- Ready continuations cannot consume tool messages because they have no pending dynamic call. They fail read-only with HTTP 409 `tool_results_without_pending_call`, preserving role and tool-call semantics.
- **Decision (2026-07-28): client tool-result replay is injection-only.** Dynamic calls use `tool_calls`; the first response drains all preceding activity before `finish_reason: "tool_calls"`, and accepted client outputs are injected into the Codex thread but never re-emitted. Replayed `dynamicToolCall` lifecycle items are likewise invisible, so they cannot appear as provider activity or change a continuation's `finish_reason`. Compatibility consequence: clients consuming the prerelease continuation echo no longer receive those client-owned `tool_calls`/`tool_results`; provider/internal observational activity is unchanged.
- **Decision (2026-07-28): terminal tool-result correlation.** A replayed full transcript may contain completed earlier tool rounds. Implicit lookup, pending-result validation, and injection use only the terminal contiguous `role: "tool"` block and the assistant tool-call message immediately before it; earlier tool exchanges are ignored for current-batch correlation. Compatibility consequence: third and later tool continuations accept full history without re-injecting earlier outputs or misclassifying current IDs as foreign.
- **Decision (2026-07-29): earlier tool rounds replay as paired history, not as a rejection.** A client that restores a saved conversation resends the whole transcript — completed tool rounds included — with a new trailing user message and no `previous_response_id`. Only a terminal tool block resolves to a continuation, so this shape opens a fresh thread, and `role: "tool"` is not a Responses item type. The fresh-thread history therefore correlates each assistant tool-call batch only with its immediately following contiguous client-result block, then injects complete pairs in assistant-declared call order, the same shape and order a continuation injects. A call no result answered and a result no immediately preceding assistant batch requested are dropped and counted in one `unpaired_history_tool_items_dropped` warning. Observational Codex activity is also omitted because its internal tool names belong to a thread that did not run it, but it is recognized rather than counted as unpaired client history. Compatibility consequence: this replaces the interim rejection that made every restored transcript fail with `Historical tool results require previous_response_id`; a call and its result now survive into the new thread instead of being flattened into an unsupported `role: "tool"` history message.
- A verbatim assistant replay may contain observational internal calls alongside pending dynamic calls. Continuation validation matches only pending call IDs, still requiring each pending call and result exactly once; duplicate assistant call IDs remain invalid.
- **Decision (2026-07-30): raw Responses items and completion define a dynamic batch.** Codex app-server can serialize callbacks from one parallel model response behind the first unanswered `item/tool/call`, so callback timing and even callback count cannot identify the batch. The proxy opts every fresh thread into `experimentalRawEvents`, captures direct declared `function_call` items, excludes call IDs replayed from submitted history, merges and deduplicates any callbacks, and closes the batch at the matching `rawResponse/completed`. Code-mode callbacks without a direct raw function item remain supported through their callback. Compatibility consequence: batching follows the upstream Responses output instead of local timing, and provider-native raw payloads remain private. The pinned `thread/resume` request has no raw-event option, so a thread first reattached after an app-server generation change cannot safely batch a newly issued dynamic tool; that response fails fast with HTTP 502 `dynamic_tool_batch_boundary_unavailable` rather than exposing a guessed partial batch.
- Parallel dynamic calls are batched and answered in observed arrival order, replacing the earlier lexicographic call-ID ordering. This is a compatibility change for clients that inferred an order from call IDs; clients must correlate by `call_id` instead.
- App-server dynamic call IDs are deduplicated within a batch by the same seen-set merge used across raw items and callbacks. The first observed call wins and no duplicate is persisted or exposed.
- Internal Codex tools are emitted as function-shaped calls/results but remain observational. They neither enter the suspension store nor become client-executable dynamic calls.

## Implementation status

Stage 05 is complete and was reworked on 2026-07-26 to the interrupt-based design above. Function-oriented offline suites cover dynamic-tool streaming and aggregation, parallel and out-of-order results, large payloads, mismatches, replay, interrupt and injection failures, transport replacement, thread serialization, continuation bindings, every fail-closed thread status, restart recovery of pending tool results, resume races, atomic state migration/rollback, and fresh-thread replay of an earlier tool round including its unpairable and observational variants. The opt-in live contract now makes parallel dispatch a provider-facing requirement: regular Responses framing must produce both independent initial calls in one batch before any tool output is supplied. Resume requires the app-server to return the exact persisted thread ID.

The opt-in live contract passed on 2026-07-14 under the original parked-turn design; its two-request `gpt-5.6-luna` function-tool round trip stayed within the then-current two-call guard, and the resulting completed response then resumed after a full proxy/app-server restart. The current contract now requires an initial two-call parallel batch and three consecutive full-history tool-result requests before that restart continuation, but has not yet been rerun with live authorization. The interrupt-based rework's protocol facts were live-verified by spikes on 2026-07-26; rerun the live contract to revalidate the expanded end-to-end round trip.
